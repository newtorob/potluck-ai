# On Windows the wheel resolved here is CPU only: its llama_cpp/lib holds
# ggml-cpu.dll and nothing else, so llama_supports_gpu_offload() is false and
# n_gpu_layers has nothing to offload to. That is the fallback backend. The GPU
# backend set is vendored separately, pinned by URL + SHA-256, by
# scripts/vendor_gpu_backend.py, which build.py runs before PyInstaller.
#
# Windows takes the wheel by direct URL for two reasons. PyPI publishes no
# win_amd64 wheel for this version, so a plain version pin makes pip try to
# compile llama.cpp from source and fail on a machine with no MSVC. And the
# vendored GPU libraries must match this wrapper's ctypes declarations exactly:
# pairing a wrapper with a native library from a different llama.cpp commit
# gives silent memory corruption rather than an honest import error. This URL
# and the pins in scripts/vendor_gpu_backend.py move together, never one alone.
#
#   sha256 31590ea000d5aff6f05f1e428048e72318a83709288159a5bd4dabec530080bb
#   7,086,788 bytes, CPU only, llama.cpp b10454
#
# Linux x86-64 uses the matching CPU wheel plus the separately vendored
# Vulkan set. Pin both to the same wrapper/native ABI. Other architectures
# retain their source build; no x86 GPU libraries are installed there.
llama-cpp-python @ https://github.com/abetlen/llama-cpp-python/releases/download/v0.3.35/llama_cpp_python-0.3.35-py3-none-win_amd64.whl ; sys_platform == "win32"

# torch is a transitive dep of sentence-transformers/umap-learn (the CPU
# embedding pipeline used by memory search). Potluck never uses torch-CUDA --
# all LLM inference goes through llama-cpp-python's own backend. Without
# pinning torch explicitly, pip resolves PyPI's DEFAULT wheel on Linux/Windows,
